Tether 0.4 · architecture

How Tether works

Tether is a self-hosted remote desktop for Windows and macOS with Linux relays. It is built on a lightly patched RustDesk core inside Tauri 2 apps, talks to its relays only over TLS WebSockets on port 443, and keeps every session end-to-end encrypted. Policies, releases and branded customer apps are signed on the administrator's PC, so a compromised relay can push neither settings nor code, and cannot read sessions by watching the traffic. A relay node also holds the server key that vouches for device keys: with it, whoever controls the ID server could impersonate a host (docs/encryption.md).

Patched RustDesk core

scripts/bootstrap.sh fetches RustDesk, hbb_common and rustdesk-server into vendor/ at pinned tags and applies patches/*.patch. Tether's changes sit behind the tauri cargo feature: the Tauri bridge src/tauri_ui (video passthrough, connection manager events), no insecure fallback, recording consent, 443-only networking and route racing in hbb_common::websocket, codec choice on low-memory hosts, and the fluxrt encode: log line. The relay patch adds WebSocket host registration, health endpoints, drain and least-loaded relay choice. scripts/make-patches.sh regenerates the patches.

Network

443-only

Tether uses exactly one outbound connection type: WebSocket over TLS on TCP 443 to the relay names. The apps force the core options allow-websocket=Y, disable-udp=Y and api-server=https://<relay>; P2P, UDP hole punching, IPv6 punching, WebRTC and LAN discovery are off and NAT/STUN probes are skipped (netpolicy.rs). Every session is relayed. Hosts keep one WebSocket open permanently, with an empty-frame heartbeat every 20 s so proxies do not close it.

Upstream hbbs accepts host registration only over UDP. The patched hbbs accepts RegisterPeer/RegisterPk over TCP/WebSocket with the same uuid, key, IP-change and rate-limit checks, keeps that connection as the host's signalling path, and gives every proxied client a unique address (forwarded IP plus connection port).

Route racing

To its own relays, Tether tries up to four routes, Happy-Eyeballs style: wss://relay on 443 and on 80, each through the detected proxy and directly. They start 300 ms apart; the first completed TLS + WebSocket handshake wins and the rest are dropped. The winner is cached per relay host and tried first next time, for /ws/id and /ws/relay. Because direct routes run alongside proxy routes, a dead proxy setting cannot keep Tether offline. Port 80 is TLS too: firewalld forwards it to Caddy's 443 listener (same certificate, same endpoints). The API, heartbeats and policy use the same racer.

Proxy detection and TLS inspection

Proxy order: HTTPS_PROXY / ALL_PROXY, then the system proxy (Windows: WinINet settings, PAC files, WPAD via WinHTTP; macOS: scutil --proxy). Detection repeats every 60 s, so VPN and network changes are picked up. HTTP CONNECT, HTTPS and SOCKS5 proxies are supported.

The relay certificate is verified by rustls. If a proxy re-signs TLS with a company CA, Tether falls back to the OS TLS stack, which trusts the CA deployed to the machine. There is never an “accept any certificate” fallback. An inspecting proxy can see the relay name, timing and sizes, and the rendezvous signalling (device ID, public key, connect requests). It cannot see the session: in the Zscaler-style test the proxy saw 1,454 relay frames whose byte statistics look like random data (printable-byte ratio 0.37).

Session flow

Every session is relayed. The viewer asks every hbbs in parallel, the hbbs that knows the host picks a relay, and both sides meet on that hbbr. Only then do the two devices run the end-to-end handshake, through the relay.

File transfer from a session. Each login of the technician app carries a random 128-bit companion_secret (inside the encrypted connection only). The file-transfer window opened from a session reuses that session's session key (peer ID, name, 64-bit session ID) and secret. The host admits such a connection without a new accept or password only while an authorized remote connection with the same key and secret is open and its Transfer files permission is on (constant-time compare). The session key alone is not secret (audit posts carry it); without the secret the customer is asked as for any connection.

Security model

The relay operator is not trusted with content: the relay forwards ciphertext. Trust is anchored in public keys compiled into the clients; private keys live on the relay (server key) or only on the admin's PC (admin and updater keys).

Keys

Admin key (Ed25519)Tether Manage, keys.jsoncompiled in: TETHER_ADMIN_PUB_KEY; relay: ADMIN_PUB_KEYPolicies, custom-app profiles, every admin API request. Several keys may be trusted for rotation.

Admin and updater keys are sealed with argon2id (64 MiB, 3 passes) + XChaCha20-Poly1305 under the admin's passphrase (≥ 8 characters, no recovery). Losing them means rebuilding every client, since new keys only work in newly built clients.

Signed policies and requests

  • Envelope: {"payload": b64, "sig": b64(ed25519), "key": b64(pubkey)}. Clients accept it only if key is one of the compiled-in admin keys and the signature verifies.
  • Rollback protection: clients store the last accepted serial and reject lower ones; the relay requires a serial higher than its current one (409). A compromised relay can withhold a policy, but cannot alter, forge or roll one back.
  • Admin requests: header Tether-Sig: v2 host=<relay host> ts=… nonce=… sig=… over "tether-admin-v2\n" + host + "\n" + METHOD + "\n" + path(with query) + "\n" + ts + "\n" + nonce + "\n" + hex(sha256(body)). The relay accepts v2 only for its own names (RELAY_HOST), allows ±300 s clock skew and rejects a nonce seen in the last 601 s (persisted across restarts). The older v1 form (no host, so not bound to one relay) is accepted from older apps until TETHER_SIG_V1=off is set on the relay. Tether Manage and the technician app sign v2 and follow no HTTP redirects.
  • Updates: minisign signature checked against the compiled-in updater key before anything runs.
  • Custom apps: the profile is an admin-signed envelope; the relay checks it before storing, and TetherQS checks it again against its own compiled-in keys.

Security floor and hardening

tether_trust::policy::FLOOR lists core options no policy can set; the apps force them on top of any policy: allow-insecure-tls-fallback, allow-remote-config-modification, enable-check-update, allow-auto-update, direct-server, enable-remote-printer, allow-auto-record-incoming/outgoing, stop-service, enable-camera, enable-terminal, allow-websocket, disable-udp, enable-lan-discovery, api-server, enable-webrtc, enable-udp-punch, enable-ipv6-punch, custom-rendezvous-server, relay-server, key.

  • A connected peer can never change this machine's settings; no third-party update checks; no virtual printer; nothing written to disk without an explicit action.
  • Tauri shell: strict CSP (default-src 'self'), no shell, filesystem or HTTP plugins; the updater, dialog, deep-link and single-instance plugins are used from Rust only and no plugin command is exposed to the webview (capabilities/default.json); DevTools not compiled into release builds. Commands that change this machine's security posture (permanent password, 2FA, options, installing the service, saving the hosts store and team tags) answer the main window only. Validated IPC input: peer IDs [A-Za-z0-9_.@:-]{1,64}, session keys 32 hex characters, options from an allow-list, bounded lengths, connection types as an enum.
  • Locked settings are refused in the backend (locked:<feature> errors), not only greyed out in the UI.

Recording consent

  1. Every incoming connection on a Tether host starts with its recording permission off, regardless of settings; the viewer's recorder is gated off before the first frame (record_state && record_permission).
  2. Record sends Misc.client_record_status = true as a request; no frame is recorded yet.
  3. The host's connection manager emits record_consent_request {conn_id, peer_name, text}; the user answers via cm_record_consent {connId, allow}.
  4. Allow turns the permission on and the viewer starts recording (REC pill); Deny sends it off again. The host can revoke at any time; a reconnect is a new connection and asks again.

recording.mode=always only automates the request. An unattended host never answers, so it is never recorded. A modified viewer could still capture frames it receives; consent is enforced by Tether's own viewer.

Policy model

A policy is one signed tether_trust::policy::Bundle: a serial, one layer per profile (technician, customer), named groups with overrides and device assignments by install uuid. 44 features in areas permissions, security, connections, video, recording, updates, policy, diagnostics and customer (full table: docs/policy.md, generated from FEATURES).

Distribution. Clients poll GET /api/policy every policy.refresh-minutes (15; 1 with policy.fast-apply) with If-None-Match: "<serial>", verify, reject lower serials, cache the verified document and apply it at the next start before the core runs. Then they send POST /api/heartbeat (uuid, ID, profile, version, OS, serial; ≤ 2048 bytes, rate-limited). The policy API, heartbeats and updates use the first server that answers.

Publishing from Tether Manage. Publishing validates the draft (unknown features or values make it unpublishable), shows a review of the change, signs it, and publishes the same signed document to every configured relay with serial = highest serial on any relay or published from this PC + 1. It then reads back each relay's state and reports per relay; a relay that missed it can be published to again, since any node with a lower serial accepts the same document. History keeps the last 50 versions per relay (policy-history/<serial>.json); restore republishes old content under a new serial, and only documents that verify with this PC's admin key are used.

Updates

  • Layout: download/<channel>/<technician|customer>/<windows-x86_64|darwin-universal>/latest.json plus versioned artifacts (Tether_<v>_x64-setup.exe, TetherQS-<v>.exe, Tether_<v>_universal.app.tar.gz + .dmg, TetherQS-<v>-universal.zip). Each platform has its own manifest; a macOS manifest lists the universal build under darwin-universal, darwin-aarch64 and darwin-x86_64.
  • Manifest: Tauri updater format plus mandatory, minimumVersion, forced. Channel from update.channel (default stable; invalid names fall back to stable). Versions order MAJOR.MINOR.PATCH[-pre] with 0.3.1-test < 0.3.1; channel switches never downgrade.
  • Technician app: the Tauri updater downloads the NSIS installer on 443 through the detected proxy, verifies it and runs it passively; the installer stops the Tether service if installed, overwrites C:\Program Files\Tether, restarts the service, and the app restarts (/R). macOS replaces Tether.app in place.
  • TetherQS: downloads (HTTPS, ≤ 200 MiB), verifies, writes TetherQS.exe.new, renames the running exe to .old and the new one into place (rollback if the second rename fails), restarts with the same ID and one-time password (hand-over file valid 60 s). Unwritable folder: %LOCALAPPDATA%\Tether-QS\TetherQS.exe. A custom app re-appends its own signed profile after verifying the plain exe. Verified 0.3.0 → 0.3.1 as a standard user through a TLS-inspecting proxy in 47 s.

High availability

Any number of independent nodes, each the full stack. No cluster protocol, no shared database; they share only the server key pair.

  1. Hosts register with every node (TETHER_SERVER list plus policy servers.list, up to 8 entries: host names or wss://host/path, verified with the same server key). One independent registration loop per server.
  2. Viewers race their request: the last server that worked first, the next one on failure or after 1 s without an answer. The first hbbs that knows the host wins.
  3. Relay choice (server side): every hbbs has a relay list of <address>[|<health URL>] entries and fetches each health URL every 3 s (2.5 s timeout). hbbr's /readyz answers 200 ready sessions=N or 503 draining sessions=N. hbbs hands out the least-loaded healthy relay; ties rotate. Locality does not matter.
  4. The host sends its RelayResponse to the same hbbs, which forwards it to the viewer; both meet on the chosen hbbr.

Drain

On SIGTERM hbbr reports not-ready at once and keeps relaying open sessions. For the first 5 s it still pairs new uuids (an hbbs may hand it out until its next check), then refuses new pairings. It exits when the last session ends or after DRAIN_TIMEOUT (systemd 300 s, Kubernetes 3600 s); a second signal exits at once. hbbs is not-ready for its own DRAIN_TIMEOUT (default 0). Health: hbbr :21121, hbbs :21122, /healthz and /readyz.

Tether Manage with N nodes: it writes to every node and the nodes stay independent. A node that missed a write is stale, not wrong. Kubernetes

Helm chart deploy/helm/tether-relay: the same design with every pod acting as a node. hbbr only pairs two halves that reach the same process, and a host's RelayResponse must reach the hbbs that holds the viewer, so load balancing either would break sessions. Every pod therefore gets a stable URL.

  • Values: publicUrl, key.existingSecret (the production key pair), hbbs.replicas 2, hbbr.replicas 2, hbbr.drainSeconds 3600 (grace = drain + 30), hbbs.drainSeconds 2, hbbs.extraRelays (e.g. the VMs), proxy.enabled (or your own ingress with 3600 s timeouts), api.enabled, podDisruptionBudget.maxUnavailable 1, requests 50m/32Mi, limits 1 CPU/256Mi.
  • Pods: UID 65532, read-only root, all capabilities dropped (Caddy keeps NET_BIND_SERVICE), RuntimeDefault seccomp, soft anti-affinity; readiness /readyz every 2 s, liveness /healthz. Image: static musl binaries on distroless (≈ 8 MB).
  • Rollouts: hbbr one pod at a time, highest ordinal first; the terminating pod is not-ready at once and every hbbs stops handing it out within 3 s; a full rollout takes at most replicas × drainSeconds. hbbs restarts take seconds and do not affect relayed sessions. A proxy rollout cuts WebSockets through the old pods (re-pair ≤ 40 ms), so do it rarely.

Custom apps

A custom app is a branded TetherQS: a signed tether_trust::custom::CustomProfile plus a private, expiring download link.

  1. Tether Manage signs the profile with the admin key and calls PUT /api/admin/custom/<id> on every relay with {profile, token, expires, channel} (≤ 300 KiB). Token: 32 random bytes, base64url, 43 characters; expiry in the future and ≤ 366 days.
  2. The relay verifies the signature against its admin keys, validates the profile, requires profile.id == <id>, and stores custom/<id>.json (0600). A new token for the same id kills the old link.
  3. GET /q/<token> (public) returns the channel's current TetherQS-<v>.exe with the trailer appended. Unknown, revoked and expired tokens all get the same 404 (no oracle); 30 requests/min per IP; downloads are counted.
  4. TetherQS reads its own file, verifies the profile against the compiled-in admin keys and applies it as the custom-app policy layer. Self-updates verify the new plain exe, then re-append the trailer.

DELETE /api/admin/custom/<id> revokes a link at once. The relay never modifies the profile. Windows-only for now (the macOS TetherQS is a .app bundle).

Diagnostics

  • Diagnostics page (diag.rs): version, ID, OS, policy serial/group/sources, server, proxy (without credentials), DNS with timing, one row per route (443/80 × proxy/direct, handshake time), last 40 ERROR/WARN lines. “Test connection” runs every route with an 8 s timeout.
  • Bundle: diagnostics.json, logs changed in the last 24 h (newest 1 MiB each, 12 MiB total), config files with every key containing password or a part equal to key, salt, token, secret, pin, otp, 2fa, tfa, trusted, pk, sk redacted. Logs are not redacted.
  • Upload: POST /api/diag/<ticket>, ticket [A-HJ-NP-Z2-9]{8} opened by an admin, 24 h, one upload, ≤ 2 MiB (else only diagnostics.json), kept 7 days. Verified round trip through a TLS-inspecting proxy: about 7 s.
  • Logs: %APPDATA%\Tether\log\<role>\ (server, cm, connect, service, portable-service), TetherQS %APPDATA%\Tether-QS\log\, macOS ~/Library/Logs/Tether/; daily or 16 MiB rotation; verbose logging for one hour from the next process start. The host encoder logs a fluxrt encode: line every 5 s.

Known limits

  • The macOS build is written but not compiled or run here; the updater, MDM path and TetherQS are tested on Windows only. Ad-hoc signed builds lose Screen Recording and Accessibility with every update. Unsigned binaries cannot be authenticated by users; Windows and macOS releases must be signed (and notarized) before distribution.
  • Update downloads try only TLS on 443 (proxy or direct), without the port-80 and proxy-to-direct fallbacks.
  • A host that only runs as a background service learns about a required update from the cache the app window writes; it may accept sessions until the app has been opened once.
  • A whole Kubernetes node freezing silently with a proxy pod on it stalls sessions until the node is NotReady (~40 s).
  • Installer: after an interactive upgrade Tether comes back via “Run Tether”; automatic reopening is guaranteed only for the in-app updater (/R).
  • Relay load is sampled every 3 s, so a burst within one interval goes to the same relay.
  • Consent needs an interactive user; a modified viewer could capture the frames it receives. Endpoint compromise is out of scope. The ID ↔ IP registry is metadata visible to the relay operator.
  • TetherQS without admin access cannot see UAC prompts or type into elevated windows. Custom apps are Windows-only.
