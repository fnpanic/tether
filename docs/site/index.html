Tether 0.6.3

User guide

Tether is a self-hosted remote-support product. A technician connects to a customer's computer by its ID, the customer agrees, and the screen, keyboard, mouse, clipboard and files travel end-to-end encrypted through your own relay servers, or directly between the two computers when the network allows it.

Technician app

“Tether”. Installed on technicians' Windows PCs and Macs. Connects to devices and can also be reached itself, also unattended.

For technicians

TetherQS

The quick-support program for customers, for Windows and macOS. Nothing to install, no admin rights. It only receives sessions.

For customers

Tether Manage

For administrators, on a Windows PC. Holds the signing keys, publishes policies, releases, the download page and branded support apps.

For administrators

Install Tether (technicians)

Windows

  1. Open your organisation's download page, for example https://relay.example.com. It detects your operating system, marks it “Your computer” and offers the matching installer. The Windows / macOS switch shows the other one.
  2. Run Tether_<version>_x64-setup.exe. It installs per machine to C:\Program Files\Tether, so Windows asks for administrator rights (UAC).
  3. Upgrades install in place. The installer closes every running Tether process itself and reopens Tether afterwards; after a manual upgrade use Run Tether on the finish page.

Only one Tether runs at a time. Starting it again brings the existing window to the front.

macOS

  1. Download Tether_<version>_universal.dmg (Apple silicon and Intel, macOS 11 or newer) and drag Tether to Applications.
  2. The current builds are not notarized. On first start, Control-click the app → Open → Open. On macOS 15 and later, try once, then System Settings → Privacy & Security → Open Anyway; macOS asks for an administrator password for that step (it changes a macOS security setting; Tether itself needs no admin rights). Without the password: xattr -dr com.apple.quarantine /Applications/Tether.app in Terminal.
  3. To be controlled remotely, allow Screen Recording and Accessibility in System Settings → Privacy & Security, then quit and reopen Tether.
macOS asks for Screen Recording although it is allowed? macOS ties Screen Recording and Accessibility to the app's signature; builds before 0.5.3 had a new one with every update, so the entry you see belongs to the old version. In Terminal run tccutil reset ScreenCapture app.tether.desktop and tccutil reset Accessibility app.tether.desktop (TetherQS: net.tether.quick), quit and reopen the app and allow it once more. From 0.5.3 on, the Mac apps are signed with one fixed certificate and keep the permissions across updates. While a permission is missing, Tether and TetherQS show a warning with Fix Screen Recording / Fix Accessibility buttons, which clear the old entry and open the right settings page (switch the app on, then choose Quit & Reopen), and the technician is told what is missing instead of waiting for the first image.

Your ID and password

The main window has two halves.

  • This device shows your Tether ID in large digits and a one-time password. The password is hidden as dots; use the eye button to show or hide it, the copy button to copy it, and New password to generate a new one. One-time passwords are 10 characters long by default.
  • Remote device is where you type the ID of the computer you want to reach. Below it you find your recent devices, with a search field.

Connect to a device

  1. Ask the customer for the ID shown in their TetherQS (or Tether) window. Spaces do not matter: 123 456 789 works.
  2. Type the ID under Remote device and click Connect. To open file transfer instead of the screen, use the Transfer files button next to it.
  3. A session window opens. Either enter the customer's one-time password, or wait while the customer clicks Accept on their side. Which of the two is possible depends on your organisation's policy.
  4. The picture appears. The toolbar shows a shield when the session is end-to-end encrypted, and which path it took (see the session toolbar).

A recent device can be opened again with one click on its card. Tether remembers the password for a device only if you tick “Remember password for this device” in the password prompt (off by default). Connecting to your own ID is refused (“That is this device's own ID: it cannot connect to itself.”).

Always encrypted. Tether refuses any connection that cannot be end-to-end encrypted. There is no “continue insecurely” button.

Hundreds of hosts: Advanced mode

Click Hosts in the main window's title bar (or Settings → Appearance → Home view) to switch the home view to Advanced; Simple view switches back. Your organisation can turn this mode off or make it the only one. It lists every device you connected to, the ones you added or imported, and, with Team turned on, your organisation's devices. It stays fast with thousands of entries.

  • Search as you type: any part of a name, ID, user, OS or note. Narrow it with tags and filters, for example #customer:acme is:online -#env:test or os:mac seen:<7d. Press ? for the full syntax.
  • Keyboard first: ↑ ↓ to move, Enter to connect, Shift+Enter for file transfer, Alt+Enter to watch without control. Ctrl+K opens a box that finds any host or command.
  • Tags such as site:berlin or customer:acme, with colours. Select many hosts (Shift+click, Ctrl+A) and press T to tag them all at once. Tag rules tag hosts automatically, for example every Mac or every name starting with BER-.
  • Saved searches, pinned hosts, names and private notes per host, and import/export as JSON or CSV. Notes stay on your PC and are left out of exports unless you include them.
  • Open sessions lists your session windows and sends Ctrl+Alt+Del, locks or restarts a remote computer without switching to it.

Details for administrators and the full search syntax: docs/advanced.md.

Command line and tether:// links

The technician app (C:\Program Files\Tether\tether.exe; macOS /Applications/Tether.app/Contents/MacOS/tether) can be started from scripts, ticket systems and intranet pages.

Links. The installer registers tether://connect/<id>. Put it into a ticket template, for example tether://connect/{{device.tether_id}}. Links never carry a password and accept nothing else, so a link alone never gives anyone access. If Tether is already running, the session opens in that app (Windows and macOS); if a session window to that device is already open, it comes to the front instead of a second one.

Passwords on the command line (--connect <id> <password> or --password) are visible in the process list and in shell history. Use them only for tests. Exit codes are listed under Exit codes.

The session toolbar

The toolbar floats at the top of the session window and hides itself after about two seconds. To bring it back, point at the small tab at the top centre of the picture for a moment or click it; the rest of the top edge belongs to the remote screen, so title bars and tabs there can be clicked. The toolbar never appears while you hold a mouse button (dragging), and it hides again shortly after the mouse leaves it. Pin it to keep it visible. Every button either works or tells you why it did not.

On the left it shows the device name, a coloured dot for the connection quality, a shield when the session is end-to-end encrypted (hover it to see the peer's fingerprint for an out-of-band check) and a badge for the path the session took: RELAY (through your relay over 443), RELAY (UDP) (through your relay, over UDP), DIRECT (LAN) (same network), DIRECT (IPV6) or P2P (directly through both routers). The first path that completes the end-to-end key exchange wins, so a direct attempt never slows the session down; behind a proxy only the relay and same-network paths are used, and policy network.direct can turn direct paths off. A VIEW ONLY badge marks a session that sends no input.

Send Ctrl+Alt+Del needs Tether installed with its service on the remote PC; UAC prompts on a TetherQS customer PC need admin access. While a UAC prompt is open there without admin access, a notice at the top of the picture says so and the session keeps running.

File transfer

Open it from the toolbar while you are connected, with Transfer files on the main window, or with tether --connect <id> --file-transfer. When opened from a running session it belongs to that session: the customer is not asked again, TetherQS shows “Transferring files” on the session card instead of a second connection, and Disconnect there ends both. File transfer is end-to-end encrypted like the screen. In tests a 64 MB file arrived intact (SHA-256 verified) through a proxy that only allowed port 443.

The window shows this computer on the left and the remote device on the right. Select files and folders as in a file manager: click selects one, Ctrl+click (Cmd on a Mac) adds or removes one, Shift+click selects a range and Ctrl+A selects everything in the pane you are in; the arrow keys (with Shift to extend), Enter and Delete work too. Upload / Download sends the whole selection (“Download 3 items”), or drag the selection to the other pane; folders are copied with everything in them. Each item is its own transfer with its own progress bar, two run at a time and the rest wait as “Queued”; the header shows how many have finished and the overall progress. Delete on the remote pane removes all selected items after one confirmation. Tether asks before it overwrites a file. New folder works on both sides, and going up from a drive root shows the list of drives.

Recording with consent

  1. Click Record session. The button shows “Waiting for the remote user to allow recording”.
  2. The remote user sees the question (default: “The technician wants to record this session. Allow?”) and chooses Allow or Deny (TetherQS: Don't allow).
  3. After Allow, a red REC pill with a timer appears and recording starts. After Deny you see “Recording declined by the other party” and nothing is written.
  4. Click again to stop. On a Tether host the remote user can also revoke the permission at any time with the “Record the session” switch; recording stops at once. A TetherQS customer ends it by ending the session.

Recordings are WebM/MP4 files of the stream you receive that any video player opens. When a recording stops, a card Recording saved shows the file name with Open and Show in folder (and the upload status if your organisation uploads recordings). The camera button next to Settings in the main window opens Recordings, which lists all recordings (date, device, length, size) with Play, Show in folder and Delete, and an Open folder button.

They are stored in %USERPROFILE%\Videos\Tether (macOS ~/Movies/Tether) and named 2026-11-05_14-03-22_<device name>_<ID>.webm. Settings → Recording shows the folder in use and lets you choose another one, unless your organisation sets the folder; it also shows whether recordings are uploaded to a share or an HTTPS address and when old ones are deleted.

Tether never records silently. Every connection asks again, also after a reconnect. An unattended computer has nobody to answer, so it cannot be recorded. If your policy is set to “always”, Tether asks automatically at the start of each session.

When the connection drops

If a working session loses its connection (network change, relay restart, Wi-Fi drop), Tether reconnects on its own:

  • The last picture stays visible, dimmed, with “Reconnecting… (attempt n)”.
  • The first retry starts at once, then after 0.25, 0.5, 1, 2, 4, 8 and then every 10 seconds. A silent relay is noticed within 3 seconds.
  • You are not asked for the password again. The picture continues as soon as the next full frame arrives. After a relay restart this typically takes about 0.9 seconds; if one relay fails completely, the session continues through the other one.
  • After 10 minutes (policy connect.reconnect-minutes) Tether shows an error with Retry.

Tether does not retry after a wrong password, when the other side rejected or ended the session, or when a policy or required update blocks the session.

Repeated wrong passwords are throttled and then blocked, and the one-time password changes after too many failures.

Unattended access on a Mac (from 0.6.3). Tether must be in Applications. After the macOS administrator prompt, Install sets up a background service (a LaunchDaemon and a LaunchAgent); Tether quits and opens again a few seconds later. The Mac is then reachable with the permanent password also with Tether closed, behind the lock screen and at the login window after signing out. From Terminal: /Applications/Tether.app/Contents/MacOS/tether --install-service; --uninstall-service removes it (do that before moving Tether to the Trash). Updates replace the app as before; the background processes restart from the new version once no session runs. Limits: with FileVault, nothing can connect after a restart until someone has unlocked the disk at the Mac; installing needs a person at the Mac (a technician cannot click Tether's own window or the macOS password prompt). The service uses the Screen Recording and Accessibility permissions Tether already has; there is nothing new to allow. On Windows, tether.exe --uninstall-service or uninstalling Tether removes the service.

Diagnostics and support

Settings → Diagnostics shows what Tether sees: version, update state, ID, system, the applied policy (serial, group and layers), the server, the proxy in use, DNS, and one row per connection route with its time. Test connection tries every route now (ports 443 and 80, each through the proxy and directly).

  • Verbose logging (1 hour): turn it on, quit Tether from the tray and start it again, reproduce the problem within the hour.
  • Export diagnostics writes tether-diagnostics-<time>.zip to Downloads. Passwords, keys, salts and tokens in the configuration are replaced by <redacted>. The log files are not redacted and can contain device IDs, IP addresses and file names.
  • Send to support: enter the 8-character code your support desk gives you and click Send to support. A code works once and for 24 hours. Tether tries every relay in turn. From the command line: tether --diag-upload <code>.
  • Open log folder opens %APPDATA%\Tether\log\ (macOS: ~/Library/Logs/Tether/).

Updates

Tether checks for updates shortly after start (within a minute), every 6 hours (policy update.check-hours), after every policy change, and when the relay announces a new release, so a published release usually reaches devices within a couple of minutes. Settings → About → Check for updates checks at once. Every update is signed by your organisation, listed in a release index signed with your organisation's admin key, and checked against it before it is installed. Your organisation may roll a release out in stages, so not every device gets it at the same moment.

You seeMeaning
Card “Update available”: Install and restart / LaterOptional update; sessions keep working
“Update required”, no LaterMandatory update or a minimum version. Sessions are blocked until it is installed.
“Tether will update” with a countdownForced update: installs after the countdown (default 60 s) and restarts. While a session runs it says “Will update after this session.” and waits: an update never ends a running session.
“Your organisation installs updates for you”Automatic updates are off; IT deploys the new version
“… none is available yet”A newer version is required but not published yet. Contact your administrator.

On Windows the installer runs in passive mode (progress only). If you are not an administrator, Windows shows a UAC prompt. On macOS the updater replaces Tether.app in place.

Start TetherQS (customers)

Your support technician sends you a link or points you to the download page. TetherQS does not install anything, needs no administrator rights and leaves no service behind: when you close the window, support ends.

  1. Windows: download TetherQS.exe (or the branded file your support company gave you, such as ACME-Support.exe) and double-click it. Windows 10 21H2 and later and Windows 11 already contain the WebView2 component it needs; if it is missing, a message tells you where to get it.
  2. Mac (macOS 11 or newer, Apple silicon and Intel): download TetherQS-<version>-universal.zip (or the branded zip from your support company), unzip it, move TetherQS out of Downloads (for example to the Desktop) and open it with Control-click → Open (macOS 15 and later: try once, then System Settings → Privacy & Security → Open Anyway). Allow Screen Recording and Accessibility when asked.
  3. The status pill shows Connecting and then Ready. Offline means it cannot reach the server; see Troubleshooting.

Give your ID and password

The window shows Your ID and a One-time password.

  • Read the ID to your technician, or copy it with the copy button.
  • The password is hidden as dots so that nobody watching your screen can read it. Click the eye to show it, and again to hide it. The copy button copies it without showing it.
  • New password makes a new one; the old one stops working.
  • Some organisations accept by click only. Then no password is shown at all and you just click Accept.

Accept or decline

When your technician connects, a card appears with who is connecting (name and ID), whether they want to see and control the screen or transfer files, and what they will be allowed to do. Only accept if you know this person.

  • Switch individual permissions on or off before you accept: Control mouse and keyboard, Use the clipboard, Transfer files, Hear this computer's sound, Restart this computer and Block my mouse and keyboard. Greyed-out switches are fixed by your support company. The name shown is chosen by the other side and is not verified; neither Accept nor Decline is pre-selected.
  • Click Accept to start, or Decline to refuse. Accept lets your technician in right away; they do not need the password then. (Telling them the one-time password works too.) A short message confirms it, and the card changes to the session view.
  • While someone asks or is connected, the window sits in the bottom-right corner of your screen, so it is always in the same place and out of the way. When the session starts it minimizes to the taskbar (Dock on a Mac); click it to bring it back. Afterwards it moves back to the middle.
  • If your organisation uses passwords only, a session with the correct password starts without the card.

During the session

  • The card shows the technician, the elapsed time and indicators for Control, Transferring files and Recording allowed.
  • You can switch permissions off at any time.
  • Chat: a tab next to Permissions on the card. A message from your technician brings the window back and opens the tab; you can reply there.
  • The red Disconnect button ends the session immediately. Closing the window does the same.

If your technician wants to record

You are asked first, every time: “The technician wants to record this session. Allow?” (your support company may use its own wording). If you choose Don't allow, nothing is recorded. If you choose Allow, the “Recording allowed” indicator appears for the rest of the session; to stop the recording, end the session with Disconnect.

Allow admin access

On Windows, TetherQS runs as a normal user. Windows hides its administrator prompts (UAC) and elevated windows from normal programs, so your technician would not see them or could not use them.

  1. Click Allow admin access (if your support company offers it).
  2. Confirm the Windows prompt. If you are not an administrator yourself, someone with administrator credentials can type them in.
  3. During a session this happens in place and the session continues. Outside a session TetherQS restarts and keeps the same ID and password.

The technician can also request admin access from inside the session; you confirm the same prompt. If you decline, TetherQS keeps running without admin rights. If your support company turned admin access off, the button is hidden and a request from the technician is refused.

Branded support apps

Your support company can give you its own version of TetherQS through a private link. It is the same program, with:

  • the company's name in the title bar and as the file name (<Name>-Support.exe, on a Mac <Name>-Support.zip),
  • its logo, accent colour and welcome text,
  • settings chosen for its customers (for example “accept by click only”).

The branding is signed by the support company; TetherQS checks the signature and falls back to the standard look if anything is wrong. The link works only until the date the company set, and can be withdrawn at any time. The same link gives you the Windows or the Mac version, whichever computer you open it on. The branding stays when TetherQS updates itself.

Help and updates

The ? in the title bar opens Help: version, ID, servers, whether each server is reachable and how fast, the proxy in use, whether admin access is on, the policy serial and the update state. It also opens without a network: the server check runs on its own (at most 5 s, with Retry) and shows the error if the server cannot be reached. Your technician may ask you to read these out. Send to support there takes the 8-character code your support desk gives you and sends TetherQS's diagnostics (logs and settings, no passwords). Check for updates checks at once and shows the result.

TetherQS updates itself when it starts, every few hours and soon after a new release is published. It downloads the new version, checks its signature, swaps the file and restarts with the same ID and password. No admin rights are needed. It never swaps itself during a session: Update then says “The update restarts TetherQS: end the session first.”, and a forced update waits until the session has ended. If an update is required, the Accept button stays disabled with “An update is required before your technician can connect.” until you click Update.

First run, keys and backup (administrators)

Tether Manage (apps/manage) runs on the administrator's Windows PC and carries the same version number as Tether and TetherQS. Its screens are Status and relays, Policy, Devices, Sessions, Team, Releases, Download page, Custom apps, Diagnostics and Keys. Its data lives in %APPDATA%\Tether-Manage (override with TETHER_MANAGE_DIR).

  1. On first start choose Create keys (or Import a backup instead). Tether Manage creates the admin key (Ed25519, signs policies and every admin request) and the updater key (minisign, signs installers and TetherQS).
  2. Choose a passphrase of at least 8 characters. The keys are sealed with it (argon2id, 64 MiB, 3 passes, then XChaCha20-Poly1305). There is no recovery.
  3. Immediately use Keys → Export backup…. It writes tether-manage-keys.tmkeys, still encrypted. Keep the backup and the passphrase in two different safe places.
  4. Later starts ask you to Unlock with the passphrase. The keys stay in memory until the app closes.
Losing both the passphrase and the backup means rebuilding every client. The public halves of both keys are compiled into the technician app and TetherQS. Without the private keys nothing you publish will be accepted by installed clients. To work from a second PC, import the same backup there.

Relays and public keys

Keys shows only public keys:

  • Admin public key → build variable TETHER_ADMIN_PUB_KEY, and ADMIN_PUB_KEY=… in /etc/tether/api.env on every relay (then restart tether-api). Several keys can be listed, comma-separated, for a key rotation.
  • Update signing public key → build variable TETHER_UPDATER_PUB_KEY for both apps.

Keys → Server key replaces the key the relays sign device identities with, without reinstalling any client (docs/key-rotation.md).

Relays (on Status and relays): add each relay by host name, for example relay.example.com and relay2.example.com (https:// is added), then Save relay list. Each address must be the relay's own https:// host name, with an optional port and nothing else. Tether Manage publishes policy, releases, the download page, tickets, custom apps and the team roster to every relay, and merges the device and session lists. The first relay is used for reads and for the links of custom apps. Each row shows Admin key accepted when the relay trusts your key (or the error), and the policy serial it serves (Live or Behind). When a relay does not answer, a publish waits until you tick “Publish to the others anyway”.

Policy editor

The policy is one signed document for all devices. Every setting is a feature (the full list is generated in docs/policy.md), and each layer can set it to one of these states:

StateEffect on the device
DefaultNot set here; the layer below decides
OnEnabled, the user may change it; the value is the default
OffDisabled and locked
LockedLocked to the given value
HiddenDisabled, locked and not shown

Layers, where later wins: built-in defaults → profile (technician or customer) → custom app (for branded TetherQS downloads) → group → machine policy set by GPO/MDM. A later layer set to On unlocks what an earlier one locked, with one exception: a custom app's setting is ignored for a feature the profile locks, so a custom app cannot switch on what the policy locks.

  • Groups: Policy → New group, give it a name and a profile, set its overrides, then assign devices on the Devices screen. Assignments take effect only after publishing.
  • Preview: the right column shows the effective policy a device would get from the draft. Locked features have a lock icon, hidden ones are struck through.
  • Validation: unknown features or invalid values make the draft “Not publishable”, so a typo never silently does nothing. The EN/DE switch only changes labels.
  • Fast apply: devices check every 15 minutes (policy.refresh-minutes). Turn on policy.fast-apply while you roll out a change and they check every minute; on a device, tether --policy-refresh applies it at once.
  • History: lists the last 50 versions on the server plus local copies. Restore publishes an old version again under a new serial.

Some protections are not features and cannot be turned off by any policy: TLS certificate checks, end-to-end encryption, 443-only networking and “no silent recording”.

Publish a policy

Publishing signs the draft with the admin key and sends it to the relays.

  1. Review. Before anything is signed, Tether Manage shows what the new version changes, so you can check it.
  2. Publish to all relays. The same signed document goes to every configured relay. Its serial is the highest serial on any relay (or published from this PC) plus 1.
  3. Read back. Tether Manage then checks what each relay serves now and reports per relay whether it has the new version. A relay that was unreachable can simply be published to again.

Devices reject a policy that is not signed by your admin key and any serial lower than the last one they accepted, so an old or tampered policy can never be pushed. The Devices screen shows which serial each device runs and highlights older ones.

Devices, sessions and team

Every app that reported in during the last 180 days (up to 50 000 devices), read from every relay. Each device sends a small heartbeat after each policy check. Filters: search, All / Active today, OS, version, profile and group.

Sessions lists what the hosts reported about incoming connections, from every relay: time, host, technician, IP, action (connected, session started, files sent or received with their paths, disconnected) and duration, for the last 24 hours up to 90 days, with search and Export CSV. Releases

  1. Build with the four release variables TETHER_SERVER, TETHER_PUB_KEY, TETHER_ADMIN_PUB_KEY, TETHER_UPDATER_PUB_KEY (macOS: bash scripts/build-macos.sh on a Mac). From 0.6.0 Tether, TetherQS and Tether Manage share one version number on Windows and macOS: bump and build all of them together, and never build a published number again.
  2. Quickest: Unlock Tether Manage → Releases → Publish the latest builds → Choose… the dist folder once → Publish N new builds…. Its review sheet sets the Rollout and Security release (see below) for all of them. Every build newer than what the relays publish is signed and published (to all relays at the same time, with progress per relay), then, on stable, the download page is rebuilt. It takes the highest version per app and platform it finds, so check that every platform's files are in the folder. The steps below publish one file (Sign and publish a new release), with Mandatory, Minimum version or Forced if needed.
  3. Unlock Tether Manage → Releases → Choose… the file. App, platform and version are read from the file name.
  4. Pick the channel (test first, later stable), write notes and set Mandatory, Minimum version or Forced only if needed. Rollout: Standard (1 % at once, 10 % after 1 h, 50 % after 6 h, 100 % after 24 h), Fast (10 %, 100 % after 1 h), Immediately, or Custom (your own shares and hours, at most 30 days). Security release skips the ramp. A device below a minimum version gets the release at once.
  5. Sign and publish. The file goes up first, then its .sig, then the signed release index (from then on the release is live on that relay), then the old-style latest.json for apps before 0.5.24. Each relay's index points at that relay's own files, and is only written once the relay has every file it names. Devices check every download against the signed index, so a relay or download mirror cannot swap a file.
  6. Check Releases on the first relay, run tether --check-update on a test device, watch the Version column on Devices, and republish the Download page if it was not rebuilt.

Rollouts lists the releases of a channel with Halt (devices that have not installed it yet stop, even if they already downloaded it), Resume and Everyone now. Publish to missing relays brings a relay that missed a publish up to date. Clean up old releases… deletes old versions on every relay after a review (it keeps the published one, a number of older ones you choose, and anything the download page links); Clean up after each publish does it automatically. Cancel stops a publish until the release index is being written; after that it is live, and Halt stops it.

Pilot channel: create a group pilot with update.channel locked to test, assign the pilot devices, publish the release to test, then to stable. A pre-release such as 0.3.1-test sorts below 0.3.1, so pilots move to the final release by themselves. Switching channel never downgrades. Never publish a version lower than the one already in a channel.

Download page

Generates the page at https://<relay>/. Design: Standard (built-in) takes a title, an introduction and which apps to offer. It has a Windows and a macOS section; visitors see their own OS first, marked “Your computer”, and the switch works without JavaScript. Apps without a stable release for an OS show “Not available yet”. Custom HTML publishes your own template with placeholders for links, versions, sizes and checksums (docs/download-page.md); it is checked before publishing. The links point to the current stable release. Publish the latest builds on stable rebuilds the page; after a release published another way, republish it.

Custom apps and private links

A custom app is a branded TetherQS for one customer or contract. You choose:

  • a name (1–64 characters; shown as the window title and used as the file name <Name>-Support.exe or <Name>-Support.zip),
  • an accent colour (#rrggbb), a welcome text (up to 400 characters) and a logo (PNG, JPEG, SVG or WebP; scaled to at most 256 × 256 px and 96 KiB),
  • settings for everyone who uses this download (customer-module features only, such as approve mode or permissions; they cannot switch on what the policy locks),
  • an expiry (1–366 days, default 30) and the update channel.
  1. Open Custom apps and click New custom app.
  2. Fill in name, logo, colour, welcome text, settings and expiry, click Review…, then Create <name>.
  3. Copy the private link and send it to the customer.

Per row: Edit changes the app and keeps the link (only on the PC that created it: “Created on another PC” otherwise), +30 days extends the link, New link replaces the link and Revoke deletes it.

Tether Manage signs this profile with the admin key and stores it on every relay under the same random link, https://<relay>/q/<token>, so the link works on any relay. Each download is the current TetherQS of that channel with the signed profile attached (the Windows file stays code-signed); it keeps its branding through self-updates. The same link serves both systems: a Mac browser gets the TetherQS zip, everything else the .exe; add /mac or /windows to the link to choose. For Macs, publish a macOS TetherQS release in the app's channel. The list shows downloads and the last download per app.

  • Revoke deletes the app: its link stops working at once.
  • Saving an app again with a new link makes the old link stop working.
  • Unknown, revoked and expired links all answer the same “not found”, and links are limited to 30 requests per minute per address. Links are not listed anywhere public; share them only with the customer.
  • Apps already downloaded keep working after a revoke (on a Mac: once they have been started).

Diagnostics tickets

  1. Diagnostics → Create ticket with a note (who and what, up to 256 characters). The ticket is opened on every relay with the same code.
  2. Read the 8-character code to the user. Codes avoid look-alike characters (no I, O, 0, 1) and work for 24 hours and one upload.
  3. The user enters it under Settings → Diagnostics → Send to support (technician app) or Help (?) → Send to support (TetherQS).
  4. Refresh the list: the ticket shows size and time, whichever relay the upload went to. Open shows the files and diagnostics.json; Save zip… stores the bundle. Uploads are kept for 7 days.
  5. Close the ticket when the case is done: no more uploads, and it moves to Archived, kept 90 days with its upload. Delete removes a ticket and its upload from every relay for good.

FAQ

Does the customer have to open ports or change the firewall?

No. Tether connects out with TLS on TCP 443 to your relay names (port 80 as a fallback). IT only needs to allow relay.example.com and relay2.example.com with WebSocket upgrades and long-lived connections. Without a proxy, Tether also tries faster direct paths (UDP to the relay's port 21116 for NAT traversal, and the local network); if they are blocked, the session stays on 443 and loses at most a fraction of a second. Behind a proxy nothing but the 443 connection leaves the network.

Does it work behind a corporate proxy or Zscaler-style TLS inspection?

Yes. Tether finds the system proxy (environment variables, WinINet, PAC files, WPAD; macOS system settings) and checks it again every minute. If the proxy re-signs TLS with a company certificate that Windows trusts, Tether accepts it. The proxy then sees device IDs and connection requests, but the session itself stays end-to-end encrypted.

Can the relay operator watch sessions?

Not by watching the traffic: the relay forwards ciphertext and never has the session keys. It knows device IDs, IP addresses and connection times, which is why you run the relay yourself. The relay's private server key vouches for which device is which, so someone who controls the ID server and holds that key could impersonate a device; keep the relays and the key secured. Details: docs/encryption.md in the repository.

Can a technician connect without the customer noticing?

Only to a device where unattended access was set up with a permanent password. TetherQS always shows an incoming session, and recording always needs the other side's consent.

Does the session always go through the relay?

No. Two computers on the same network connect directly (Direct (LAN)), and without a proxy Tether also tries a direct path over IPv6 or through both routers (Direct (IPv6), P2P) or your relay over UDP (Relay (UDP)). Every path is end-to-end encrypted and checks the same password, Accept and permissions. Policy network.direct set to off keeps every session on the relay.

What happens if one relay fails?

Devices are registered with every relay. A session running through the failed relay reconnects through another one by itself (about a second in tests; longer while the relays notice the failure); new sessions use whichever relay answers. Relays can also be set up as backups that take sessions only while no main relay is healthy.

Why is a setting greyed out?

Your organisation's policy locks it. Settings → Diagnostics → Policy shows the serial, group and the layers that applied.
