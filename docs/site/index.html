Tether 0.4

User guide

Tether is a self-hosted remote-support product. A technician connects to a customer's computer by its ID, the customer agrees, and the screen, keyboard, mouse, clipboard and files travel end-to-end encrypted through your own relay servers.

Technician app

“Tether”. Installed on technicians' Windows PCs and Macs. Connects to devices and can also be reached itself.

For technicians

TetherQS

The quick-support program for customers. One portable file: no installation, no admin rights. It only receives sessions.

For customers

Tether Manage

For administrators. Holds the signing keys, publishes policies, releases, the download page and branded support apps.

For administrators

Install Tether (technicians)

Windows

  1. Open your organisation's download page, for example https://tether-desk.duckdns.org. It detects your operating system, marks it “Your computer” and offers the matching installer. The Windows / macOS switch shows the other one.
  2. Run Tether_<version>_x64-setup.exe. It installs per machine to C:\Program Files\Tether, so Windows asks for administrator rights (UAC).
  3. Upgrades install in place. The installer closes every running Tether process itself and reopens Tether afterwards; after a manual upgrade use Run Tether on the finish page.

Only one Tether runs at a time. Starting it again brings the existing window to the front.

macOS

  1. Download Tether_<version>_universal.dmg (Apple silicon and Intel, macOS 11 or newer) and drag Tether to Applications.
  2. The current builds are not notarized. On first start, Control-click the app → Open → Open. On macOS 15 and later, try once, then System Settings → Privacy & Security → Open Anyway; macOS asks for an administrator password for that step (it changes a macOS security setting; Tether itself needs no admin rights). Without the password: xattr -dr com.apple.quarantine /Applications/Tether.app in Terminal.
  3. To be controlled remotely, allow Screen Recording and Accessibility in System Settings → Privacy & Security, then quit and reopen Tether.
macOS asks for Screen Recording although it is allowed? macOS ties Screen Recording and Accessibility to the app's signature; builds before 0.5.3 had a new one with every update, so the entry you see belongs to the old version. In Terminal run tccutil reset ScreenCapture app.tether.desktop and tccutil reset Accessibility app.tether.desktop (TetherQS: net.tether.quick), quit and reopen the app and allow it once more. From 0.5.3 on, the Mac apps are signed with one fixed certificate and keep the permissions across updates. While a permission is missing, Tether and TetherQS show a warning with buttons that open the right settings page, and the technician is told what is missing instead of waiting for the first image.

Your ID and password

The main window has two halves.

  • This device shows your Tether ID in large digits and a one-time password. The password is hidden as dots; use the eye button to show or hide it, the copy button to copy it, and New password to generate a new one. One-time passwords are 10 characters long by default.
  • Remote device is where you type the ID of the computer you want to reach. Below it you find your recent devices, with a search field.

Connect to a device

  1. Ask the customer for the ID shown in their TetherQS (or Tether) window. Spaces do not matter: 123 456 789 works.
  2. Type the ID under Remote device and click Connect. To open file transfer instead of the screen, use the Transfer files button next to it.
  3. A session window opens. Either enter the customer's one-time password, or wait while the customer clicks Accept on their side. Which of the two is possible depends on your organisation's policy.
  4. The picture appears. The toolbar shows a shield when the session is end-to-end encrypted.

A recent device can be opened again with one click on its card. Tether remembers the password for a device only if you leave “Remember” switched on in the password prompt.

Always encrypted. Tether refuses any connection that cannot be end-to-end encrypted. There is no “continue insecurely” button.

Command line and tether:// links

The technician app (C:\Program Files\Tether\tether.exe) can be started from scripts, ticket systems and intranet pages.

CommandWhat it does
tether --connect <id>Open a session window to <id>
--password-stdin / --password-env VARRead the password from standard input or an environment variable (recommended)
--file-transferOpen file transfer instead of the screen
--view-onlyWatch only, send no mouse or keyboard input
--fullscreenOpen the session in full screen
--get-id, --versionPrint this device's ID or the version
--check-updateCheck for an update now, e.g. update 0.3.1 available (installed 0.3.0)
--policy-refreshFetch and apply the organisation policy now
--diagnostics <out.zip>Write a diagnostics archive
--helpShow the list
# PowerShell: connect with a password from a secret store, without showing it on the command line
Get-Secret -Name 'host-123456789' -AsPlainText | & "C:\Program Files\Tether\tether.exe" --connect 123456789 --password-stdin

Links. The installer registers tether://connect/<id>. Put it into a ticket template, for example tether://connect/{{device.tether_id}}. Links never carry a password and accept nothing else, so a link alone never gives anyone access. If Tether is already running, the session opens in that app.

Passwords on the command line (--connect <id> <password> or --password) are visible in the process list and in shell history. Use them only for tests. Exit codes are listed under Exit codes.

The session toolbar

The toolbar floats at the top of the session window and hides itself after about two seconds. To bring it back, point at the small tab at the top centre of the picture for a moment or click it; the rest of the top edge belongs to the remote screen, so title bars and tabs there can be clicked. The toolbar never appears while you hold a mouse button (dragging), and it hides again shortly after the mouse leaves it. Pin it to keep it visible. Every button either works or tells you why it did not.

On the left it shows the device name, a coloured dot for the connection quality, a shield when the session is end-to-end encrypted (hover it to see the peer's fingerprint for an out-of-band check) and a RELAY badge: Tether sessions always run through your relay.

Some functions can be disabled by your organisation or by the remote user (control, clipboard, file transfer, audio, restart). The Send Ctrl+Alt+Del and UAC prompts on a TetherQS customer PC need admin access.

File transfer

Open it from the toolbar while you are connected, with Transfer files on the main window, or with tether --connect <id> --file-transfer. When opened from a running session it belongs to that session: the customer is not asked again, TetherQS shows “Transferring files” on the session card instead of a second connection, and Disconnect there ends both. File transfer is end-to-end encrypted like the screen. In tests a 64 MB file arrived intact (SHA-256 verified) through a proxy that only allowed port 443.

The window shows this computer on the left and the remote device on the right. Select files and folders as in a file manager: click selects one, Ctrl+click (Cmd on a Mac) adds or removes one, Shift+click selects a range and Ctrl+A selects everything in the pane you are in; the arrow keys (with Shift to extend), Enter and Delete work too. Upload / Download sends the whole selection (“Download 3 items”), or drag the selection to the other pane; folders are copied with everything in them. Each item is its own transfer with its own progress bar, two run at a time and the rest wait as “Queued”; the header shows how many have finished and the overall progress. Delete on the remote pane removes all selected items after one confirmation.

Recording with consent

  1. Click Record session. The button shows “Waiting for the remote user to allow recording”.
  2. The remote user sees the question (default: “The technician wants to record this session. Allow?”) and chooses Allow or Deny.
  3. After Allow, a red REC pill with a timer appears and recording starts. After Deny you see “Recording declined by the other party” and nothing is written.
  4. Click again to stop. The remote user can also revoke the permission at any time; recording stops at once.

Recordings are WebM/MP4 files of the stream you receive that any video player opens. When a recording stops, a card Recording saved shows the file name with Open and Show in folder (and the upload status if your organisation uploads recordings). The camera button next to Settings in the main window opens Recordings, which lists all recordings (date, device, length, size) with Play, Show in folder and Delete, and an Open folder button.

They are stored in %USERPROFILE%\Videos\Tether (macOS ~/Movies/Tether) and named 2026-11-05_14-03-22_<device name>_<ID>.webm. Settings → Recording shows the folder in use and lets you choose another one, unless your organisation sets the folder; it also shows whether recordings are uploaded to a share or an HTTPS address and when old ones are deleted.

Tether never records silently. Every connection asks again, also after a reconnect. An unattended computer has nobody to answer, so it cannot be recorded. If your policy is set to “always”, Tether asks automatically at the start of each session.

When the connection drops

If a working session loses its connection (network change, relay restart, Wi-Fi drop), Tether reconnects on its own:

  • The last picture stays visible, dimmed, with “Reconnecting… (attempt n)”.
  • The first retry starts at once, then after 0.25, 0.5, 1, 2, 4, 8 and then every 10 seconds. A silent relay is noticed within 3 seconds.
  • You are not asked for the password again. The picture continues as soon as the next full frame arrives. After a relay restart this typically takes about 0.9 seconds; if one relay fails completely, the session continues through the other one.
  • After 10 minutes (policy connect.reconnect-minutes) Tether shows an error with Retry.

Tether does not retry after a wrong password, when the other side rejected or ended the session, or when a policy or required update blocks the session.

Diagnostics and support

Settings → Diagnostics shows what Tether sees: version, ID, system, the applied policy (serial, group and layers), the server, the proxy in use, DNS, and one row per connection route with its time. Test connection tries every route now (ports 443 and 80, each through the proxy and directly).

  • Verbose logging (1 hour): turn it on, quit Tether from the tray and start it again, reproduce the problem within the hour.
  • Export diagnostics writes tether-diagnostics-<time>.zip to Downloads. Passwords, keys, salts and tokens in the configuration are replaced by <redacted>. The log files are not redacted and can contain device IDs, IP addresses and file names.
  • Send to support: enter the 8-character code your support desk gives you and click Send to support. A code works once and for 24 hours.
  • Open log folder opens %APPDATA%\Tether\log\ (macOS: ~/Library/Logs/Tether/).

Updates

Tether checks for updates 5 seconds after start, every 6 hours (policy update.check-hours) and after every policy change. Every update is signed by your organisation and checked before it is installed.

On Windows the installer runs in passive mode (progress only). If you are not an administrator, Windows shows a UAC prompt.

Start TetherQS (customers)

Your support technician sends you a link or points you to the download page. TetherQS is one file. It does not install anything, needs no administrator rights and leaves no service behind: when you close the window, support ends.

  1. Windows: download TetherQS.exe (or the branded file your support company gave you, such as ACME-Support.exe) and double-click it. Windows 10 21H2 and later and Windows 11 already contain the WebView2 component it needs; if it is missing, a message tells you where to get it.
  2. Mac: download TetherQS-<version>-universal.zip, unzip it, move TetherQS out of Downloads (for example to the Desktop) and open it with Control-click → Open. Allow Screen Recording and Accessibility when asked.
  3. The status pill shows Connecting and then Ready. Offline means it cannot reach the server; see Troubleshooting.

Give your ID and password

The window shows Your ID and a One-time password.

  • Read the ID to your technician, or copy it with the copy button.
  • The password is hidden as dots so that nobody watching your screen can read it. Click the eye to show it, and again to hide it. The copy button copies it without showing it.
  • New password makes a new one; the old one stops working.
  • Some organisations accept by click only. Then no password is shown at all and you just click Accept.
Masked password. Hiding the password with an eye button is how the technician app already works; TetherQS gets the same behaviour in the current release. If your TetherQS still shows the password in plain text, it is an older version.

Accept or decline

When your technician connects, a card appears with who is connecting (name and ID), whether they want to see and control the screen or transfer files, and what they will be allowed to do. Only accept if you know this person.

  • Switch individual permissions on or off before you accept: Control (mouse and keyboard), Files (file transfer), clipboard, audio and restart. Greyed-out switches are fixed by your support company.
  • Click Accept to start, or Decline to refuse. Accept lets your technician in right away; they do not need the password then. (Telling them the one-time password works too.) A short message confirms it, and the card changes to the session view.
  • While someone asks or is connected, the window sits in the bottom-right corner of your screen, so it is always in the same place and out of the way. Afterwards it moves back to the middle.
  • If your organisation uses passwords only, a session with the correct password starts without the card.

During the session

  • The card shows the technician, the elapsed time and indicators for Control, Files and REC.
  • You can switch permissions off at any time.
  • The red Disconnect button ends the session immediately. Closing the window does the same.

If your technician wants to record

You are asked first, every time: “The technician wants to record this session. Allow?” (your support company may use its own wording). If you choose Deny, nothing is recorded. If you choose Allow, the REC indicator appears, and you can withdraw the permission at any time with the “Record the session” switch.

Allow admin access

TetherQS runs as a normal user. Windows hides its administrator prompts (UAC) and elevated windows from normal programs, so your technician would see a black or frozen screen there.

  1. Click Allow admin access (if your support company offers it).
  2. Confirm the Windows prompt. If you are not an administrator yourself, someone with administrator credentials can type them in.
  3. During a session this happens in place and the session continues. Outside a session TetherQS restarts and keeps the same ID and password.

The technician can also request admin access from inside the session; you confirm the same prompt. If you decline, TetherQS keeps running without admin rights.

Branded support apps

Your support company can give you its own version of TetherQS through a private link. It is the same program, with:

  • the company's name in the title bar and as the file name (<Name>-Support.exe),
  • its logo, accent colour and welcome text,
  • settings chosen for its customers (for example “accept by click only”).

The branding is signed by the support company; TetherQS checks the signature and falls back to the standard look if anything is wrong. The link works only until the date the company set, and can be withdrawn at any time. Branded apps are available for Windows.

Help and updates

The ? in the title bar opens Help: version, ID, server, whether the server is reachable and how fast, the proxy in use, whether admin access is on, and the policy serial. It also opens without a network: the server check runs on its own (at most 5 s, with Retry) and shows the error if the server cannot be reached. Your technician may ask you to read these out.

TetherQS updates itself when it starts and every few hours. It downloads the new version, checks its signature, swaps the file and restarts with the same ID and password. No admin rights are needed. If an update is required, the Accept button stays disabled with “An update is required before your technician can connect.” until you click Update.

First run, keys and backup (administrators)

Tether Manage (apps/manage) runs on the administrator's PC. Its screens are Status, Policy, Devices, Releases, Download page, Diagnostics, and Keys and server. Its data lives in %APPDATA%\Tether-Manage (override with TETHER_MANAGE_DIR).

  1. On first start choose Create keys (or Import a backup instead). Tether Manage creates the admin key (Ed25519, signs policies and every admin request) and the updater key (minisign, signs installers and TetherQS).
  2. Choose a passphrase of at least 8 characters. The keys are sealed with it (argon2id, 64 MiB, 3 passes, then XChaCha20-Poly1305). There is no recovery.
  3. Immediately use Keys and server → Export backup…. It writes tether-manage-keys.tmkeys, still encrypted. Keep the backup and the passphrase in two different safe places.
  4. Later starts ask you to Unlock with the passphrase. The keys stay in memory until the app closes.
Losing both the passphrase and the backup means rebuilding every client. The public halves of both keys are compiled into the technician app and TetherQS. Without the private keys nothing you publish will be accepted by installed clients. To work from a second PC, import the same backup there.

Relays and public keys

Keys and server shows only public keys:

  • Admin public key → build variable TETHER_ADMIN_PUB_KEY, and ADMIN_PUB_KEY=… in /etc/tether/api.env on every relay (then restart tether-api). Several keys can be listed, comma-separated, for a key rotation.
  • Update signing public key → build variable TETHER_UPDATER_PUB_KEY for both apps.

Relay address: one or more https:// addresses, comma-separated, for example https://tether-desk.duckdns.org, https://tether-desk2.duckdns.org. Tether Manage publishes policy, releases, the download page, tickets and custom apps to every relay, and merges the device lists. The Status screen shows “Connected, admin key accepted” when a relay trusts your key.

Policy editor

The policy is one signed document for all devices. Every setting is a feature (the full list is generated in docs/policy.md), and each layer can set it to one of these states:

StateEffect on the device
DefaultNot set here; the layer below decides
OnEnabled, the user may change it; the value is the default
OffDisabled and locked
LockedLocked to the given value
HiddenDisabled, locked and not shown

Layers, where later wins: built-in defaults → profile (technician or customer) → custom app (for branded TetherQS downloads) → group → machine policy set by GPO/MDM. A later layer set to On unlocks what an earlier one locked.

  • Groups: Policy → New group, give it a name and a profile, set its overrides, then assign devices on the Devices screen. Assignments take effect only after publishing.
  • Preview: the right column shows the effective policy a device would get from the draft. Locked features have a lock icon, hidden ones are struck through.
  • Validation: unknown features or invalid values make the draft “Not publishable”, so a typo never silently does nothing. The EN/DE switch only changes labels.
  • Fast apply: devices check every 15 minutes (policy.refresh-minutes). Turn on policy.fast-apply while you roll out a change and they check every minute; on a device, tether --policy-refresh applies it at once.
  • History: lists the last 50 versions on the server plus local copies. Restore publishes an old version again under a new serial.

Some protections are not features and cannot be turned off by any policy: TLS certificate checks, end-to-end encryption, 443-only networking and “no silent recording”.

Publish a policy

Publishing signs the draft with the admin key and sends it to the relays.

  1. Review. Before anything is signed, Tether Manage shows what the new version changes, so you can check it.
  2. Publish to all relays. The same signed document goes to every configured relay. Its serial is the highest serial on any relay (or published from this PC) plus 1.
  3. Read back. Tether Manage then checks what each relay serves now and reports per relay whether it has the new version. A relay that was unreachable can simply be published to again.

Devices reject a policy that is not signed by your admin key and any serial lower than the last one they accepted, so an old or tampered policy can never be pushed. The Devices screen shows which serial each device runs and highlights older ones.

Devices

Every app that reported in during the last 180 days (up to 10 000 devices). Each device sends a small heartbeat after each policy check.

Releases

  1. Build with the four release variables TETHER_SERVER, TETHER_PUB_KEY, TETHER_ADMIN_PUB_KEY, TETHER_UPDATER_PUB_KEY (macOS: bash scripts/build-macos.sh on a Mac).
  2. Quickest: Unlock Tether Manage → Releases → Publish the latest builds → Choose… the dist folder once → Publish N new builds…. Every build newer than what the relays publish is signed and published, then the download page is rebuilt. The steps below publish one file, with Mandatory, Minimum version or Forced if needed.
  3. Unlock Tether Manage → Releases → Choose… the file. App, platform and version are read from the file name.
  4. Pick the channel (test first, later stable), write notes and set Mandatory, Minimum version or Forced only if needed.
  5. Sign and publish. The file goes up first, then its .sig, then latest.json, so a client never sees a manifest that points to a missing file. Each relay's manifest points at that relay.
  6. Check Files on the server, run tether --check-update on a test device, watch the Version column on Devices, and republish the Download page.

Staged rollout: create a group pilot with update.channel locked to test, assign the pilot devices, publish the release to test, then to stable. A pre-release such as 0.3.1-test sorts below 0.3.1, so pilots move to the final release by themselves. Switching channel never downgrades. Never publish a version lower than the one already in a channel.

Download page

Generates the page at https://<relay>/: a title, an introduction and which apps to offer. It has a Windows and a macOS section; visitors see their own OS first, marked “Your computer”, and the switch works without JavaScript. Apps without a stable release for an OS show “Not available yet”. The links point to the current stable release, so republish the page after every release.

Custom apps and private links

A custom app is a branded TetherQS for one customer or contract. You choose:

  • a name (1–64 characters; shown as the window title and used as the file name <Name>-Support.exe),
  • an accent colour (#rrggbb), a welcome text (up to 400 characters) and a PNG logo (up to 96 KiB),
  • settings for everyone who uses this download (customer-module features only, such as approve mode or permissions),
  • an expiry (at most 366 days) and the update channel.
  1. Open Custom apps and click New custom app.
  2. Fill in name, logo, colour, welcome text, settings and expiry, then click Create <name>.
  3. Copy the private link and send it to the customer.

Per row: Edit changes the app (only on the PC that created it: “Created on another PC” otherwise), New link replaces the link and Revoke deletes it.

Tether Manage signs this profile with the admin key and stores it on every relay under the same random link, https://<relay>/q/<token>, so the link works on any relay. Each download is the current TetherQS of that channel with the signed profile attached; it keeps its branding through self-updates. The list shows downloads and the last download per app.

  • Revoke deletes the app: its link stops working at once.
  • Saving an app again with a new link makes the old link stop working.
  • Unknown, revoked and expired links all answer the same “not found”, and links are limited to 30 requests per minute per address. Links are not listed anywhere public; share them only with the customer.
  • Custom apps are Windows-only for now.

Diagnostics tickets

  1. Diagnostics → Create ticket with a note (who and what, up to 256 characters). The ticket is opened on every relay with the same code.
  2. Read the 8-character code to the user. Codes avoid look-alike characters (no I, O, 0, 1) and work for 24 hours and one upload.
  3. The user enters it under Settings → Diagnostics → Send to support.
  4. Refresh the list: the ticket shows size and time. Open shows the files and diagnostics.json; Save zip… stores the bundle. Uploads are kept for 7 days.

FAQ

Does the customer have to open ports or change the firewall?

No. Tether only makes outgoing TLS connections on TCP 443 to your relay names (port 80 as a fallback). IT only needs to allow tether-desk.duckdns.org and tether-desk2.duckdns.org with WebSocket upgrades and long-lived connections.

Does it work behind a corporate proxy or Zscaler-style TLS inspection?

Yes. Tether finds the system proxy (environment variables, WinINet, PAC files, WPAD; macOS system settings) and checks it again every minute. If the proxy re-signs TLS with a company certificate that Windows trusts, Tether accepts it. The proxy still sees only encrypted session data.

Can the relay operator watch sessions?

No. The relay forwards ciphertext. It knows device IDs, IP addresses and connection times, which is why you run the relay yourself.

Can a technician connect without the customer noticing?

Only to a device where unattended access was set up with a permanent password. TetherQS always shows an incoming session, and recording always needs the other side's consent.

What happens if one relay fails?

Devices are registered with every relay. A running session moves to the other relay in about a second; new sessions use whichever relay answers.

Why is a setting greyed out?

Your organisation's policy locks it. Settings → Diagnostics → Policy shows the serial, group and the layers that applied.

Troubleshooting

Start with the Diagnostics page (TetherQS: ? → Help), then ask for a diagnostics bundle with a ticket code.
