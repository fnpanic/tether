# Tether relay API (`tether-api`) — wire contract

The contract between the technician app (`apps/desktop`), the customer module (`apps/quick`), the
management app (`apps/manage`) and the relay service (`server/api`). Shared types and crypto live
in `crates/tether-trust`; do not reimplement them.

Base URL: `https://<relay>` (production `https://tether-desk.duckdns.org`). With several servers
(compiled-in `TETHER_SERVER` list plus policy `servers.list`) clients use the first one that answers,
the last one that answered first; every server must serve the same API and releases. Caddy routes:
- `/api/*` → `tether-api` on `127.0.0.1:21120`
- `/download/*` → static files in `/var/lib/tether-api/download/` (served by Caddy `file_server`;
  `latest.json` with `Cache-Control: no-cache`)
- `/` → `/var/lib/tether-api/download/index.html` (the download page)
- `/ws/id` and `/ws/relay` are unchanged.

Clients reach the API through the same route racer as the relay (443/80, proxy/direct), using the
system proxy. Everything is TLS; plain HTTP is never used.

## Keys

| Key | Holder | Public half lives in |
| --- | --- | --- |
| Admin key (Ed25519) | management app, encrypted at rest | clients: compile-time `TETHER_ADMIN_PUB_KEY` (base64); server: `ADMIN_PUB_KEY` in `/etc/tether/api.env` |
| Updater key (Tauri minisign) | management app, encrypted at rest | compile-time `TETHER_UPDATER_PUB_KEY` (technician app and customer module) |
| Server key (Ed25519, hbbs/hbbr) | relays (`/var/lib/tether/id_ed25519`); new ones generated by the management app for a rotation | clients: compile-time `TETHER_PUB_KEY`, replaced by the signed server key list below ([key-rotation.md](key-rotation.md)) |

Several admin public keys may be trusted (comma-separated) to allow key rotation.

## Signed documents

`tether_trust::envelope::Signed` JSON: `{"payload": b64(bytes), "sig": b64(sig), "key": b64(pubkey)}`.
The payload of a policy document is the JSON of `tether_trust::policy::Bundle`; of a server key
list, `tether_trust::serverkeys::KeyList`: `{"serial":3,"issued_at":…,"keys":[{"key":"<b64>","not_before":0,"expires":0}]}`
(1–8 keys, at least one without `expires`; the first active key is the one clients present).

## Public endpoints (no auth)

### `GET /api/policy`
Returns the stored signed policy document (`application/json`), or `404` if none was published.
Clients verify it with `envelope::open_json(raw, &[admin keys])`, parse with `Bundle::from_json`,
reject `serial` lower than the last accepted one (stored locally), then `policy::resolve`.
Response header `ETag: "<serial>"`; clients send `If-None-Match` and get `304` when unchanged.

### `GET /api/server-keys`
The signed server key list (`404` if none was published), served and cached like the policy:
`ETag: "<serial>"`, `If-None-Match` → `304`. Clients verify it with the admin keys
(`serverkeys::KeyList::open`), reject a serial lower than the cached one or the stored floor
(`serverkeys::accept`, `server-keys.serial`), fetch it before every policy check and cache it as
`server-keys.json`. Clients stop reading after 16 KiB + 1 byte (`tether_trust::read_limited`); the
policy is read the same way with its own limit. See
[key-rotation.md](key-rotation.md).

### `POST /api/heartbeat`
Body (JSON, ≤ 2048 bytes, unknown fields rejected):
```json
{"uuid":"<install uuid, 8-64 [A-Za-z0-9-]>","id":"<Tether ID, ≤ 32>","profile":"technician|customer",
 "version":"0.3.0","os":"windows 10.0.26300","serial":12,"server_keys_serial":3}
```
`server_keys_serial` (optional, default 0): the server key list the device applied. Clients send
it only once they have a list, so relay APIs from before it keep accepting their heartbeats.
`204` on success. `429` when the same uuid posts more than once per 60 s or an IP more than 30 per
minute. The server stores `{…, "ip": <client ip from X-Forwarded-For>, "last_seen": unix}` per uuid,
at most 10 000 devices (oldest `last_seen` evicted), entries older than 180 days dropped.
Clients send it after each policy check.

### `POST /api/diag/<ticket>`
Upload a diagnostics zip for a ticket an admin opened. `<ticket>` is 8 characters `[A-HJ-NP-Z2-9]`
(no ambiguous letters). Body `application/zip`, ≤ 2 MiB. `204` if the ticket is open and
unused, else `404`. One upload per ticket. Stored 7 days.

### `POST /api/audit/conn`, `POST /api/audit/file`, `POST /api/audit/alarm` (session audit log)
The host side of every Tether app (`vendor/rustdesk/src/server/connection.rs`, `post_conn_audit` /
`post_file_audit` / `post_alarm_audit`, RustDesk Pro shape) posts one record per event to
`<api-server>/api/audit/<kind>`. `api-server` is `https://<first TETHER_SERVER host>`
(`netpolicy.rs`), so every host posts to the **first relay of its build**, through Caddy's
`/api/*` route; Tether Manage reads every relay and merges. Bodies (JSON, ≤ 8 KiB, unknown fields
rejected), all with `"id"` (Tether ID, ≤ 32), `"uuid"` (base64 machine uuid, ≤ 128; not the
heartbeat install uuid), `"conn_id"` (per-process connection number) and `"nonce"` (unique per
record, ≤ 64 `[A-Za-z0-9-]`):
```
conn, TCP connection opened:  {"action":"new","ip":"<technician ip>","session_id":0,…}
conn, technician logged in:   {"peer":["<technician id>","<technician name>"],"type":0,"primary_auth":1,"two_factor":1,"session_id":<u64>,…}
conn, connection closed:      {"action":"close","session_id":<u64>,…}
file, files sent/received:    {"peer_id":"…","type":0,"path":"<folder or file>","is_file":false,
                               "info":"{\"ip\":\"…\",\"name\":\"<technician name>\",\"num\":12,\"files\":[[\"name\",size],…≤10]}",…}
alarm (whitelist block, …):   {"typ":0,"info":"<JSON text ≤ 1024>",…}
```
`type` (conn): 0 remote, 1 file transfer, 2 port forward, 3 camera, 4 terminal. `type` (file):
0 = the host sent files to the technician, 1 = the host received files. `primary_auth`: 1 click,
2 one-time password, 3 permanent password, 4 switch sides. Optional `conn_audit_ref` (≤ 128).

Answers: `204` with an empty body when stored (also when the same `nonce` was stored in the last
10 minutes: a client retry), `400` invalid (the client drops it), `413` too large, `429` more than
120 posts/min from one IP or 60/min from one device `uuid` (the client retries 429 and 5xx for up
to 120 s), `507` disk low or the log at its size cap. Not authenticated: see SECURITY.md
"Session audit log". Records never change devices, policy or anything else on the relay.

Stored record (one JSON line in `audit/<YYYY-MM-DD>.jsonl`, UTC day; files `0600`):
`{"ts": <server unix time>, "src": "<poster ip from X-Forwarded-For>", "kind": "conn|file|alarm",
"action": "connect|login|disconnect|send|receive|alarm", "id", "uuid", "conn_id", "nonce", …}` plus,
when present: `session_id` (string, u64), `ip` (technician address as the host saw it), `peer_id`,
`peer_name`, `conn_type` (`remote`, `file_transfer`, `port_forward`, `view_camera`, `terminal`),
`primary_auth` (`click`, `temporary_password`, `permanent_password`, `switch_sides`),
`two_factor`, `ref`, `path`, `is_file`, `num`, `files`, `typ`, `info`.

Retention (`/etc/tether/api.env`, read at start): `AUDIT_RETENTION_DAYS` (default 90; whole UTC
days; `0` = accept and store nothing), `AUDIT_MAX_MB` (default 50; above it the oldest days are
deleted, never today's; if today's file alone reaches the cap, new records get `507`). Applied at
start and every minute.

## Admin endpoints (signed requests)

Every request carries `Tether-Sig: v1 ts=… nonce=… sig=…` (see `tether_trust::reqauth`; the path
includes the query string; body hash covers the exact bytes sent). The server verifies against
every trusted admin key, allows ±300 s clock skew, and rejects a nonce seen in the last 600 s.
Failure: `401` with a short reason. Bodies over the limits: `413`.

| Method & path | Body | Result |
| --- | --- | --- |
| `PUT /api/admin/policy` | signed policy document (≤ 256 KiB) | `204`. The server also verifies the signature, validates the bundle and requires `serial` > current (`409` otherwise). Stored atomically, previous versions kept in `policy-history/<serial>.json` (last 50). |
| `PUT /api/admin/server-keys` | signed server key list (≤ 16 KiB) | `204`. Verified against the admin keys, validated (`KeyList::validate`), `serial` > current (`409` otherwise). Stored as `server-keys.json`. |
| `GET /api/admin/policy-history` | – | `[{"serial":…, "issued_at":…}]` newest first |
| `GET /api/admin/policy-history/<serial>` | – | the signed document exactly as published (`404` if not kept) |
| `GET /api/admin/devices` | – | `[{uuid,id,profile,version,os,serial,server_keys_serial,ip,last_seen}]` |
| `POST /api/admin/diag-ticket` | `{"note":"…"}` (≤ 256 chars) | `{"ticket":"K7Q2M9XD","expires":unix}` (open 24 h) |
| `GET /api/admin/diag` | – | `[{ticket,note,created,uploaded,size}]` |
| `GET /api/admin/diag/<ticket>` | – | the zip (`application/zip`) or `404` |
| `PUT /api/admin/release/<channel>/<path>` | file bytes (≤ 200 MiB) | `204`. Writes `download/<channel>/<path>` atomically. `<channel>` `[a-z0-9-]{1,32}`; `<path>` segments `[A-Za-z0-9._-]`, no `..`. Upload artifacts first, `latest.json` last. |
| `DELETE /api/admin/release/<channel>/<path>` | – | `204` |
| `GET /api/admin/releases` | – | `[{channel,path,size,modified}]` |
| `PUT /api/admin/download-page` | HTML (≤ 512 KiB) | `204`, stored as `download/index.html` |
| `GET /api/admin/audit?since=<unix>&limit=<n>&device=<id or uuid>` | – | Session audit records (above), newest first. All optional: `since` (default 0), `limit` 1–5000 (default 1000), `device` matches `id` or `uuid` exactly (URL-encoded). Unknown parameter or bad value: `400`. |
| `GET /api/admin/status` | – | `{version, disk_free, devices, policy_serial, server_keys_serial, uptime}` |

The server refuses uploads that would leave less than 2 GiB free on the disk (`507`).

## Download layout and update manifests

```
download/
  index.html                                  download page
  <channel>/technician/windows-x86_64/latest.json
  <channel>/technician/windows-x86_64/Tether_<v>_x64-setup.exe(.sig)
  <channel>/customer/windows-x86_64/latest.json
  <channel>/customer/windows-x86_64/TetherQS-<v>.exe(.sig)   versioned, so uploads never touch the live file
  <channel>/technician/darwin-universal/latest.json
  <channel>/technician/darwin-universal/Tether_<v>_universal.app.tar.gz(.sig)   updater archive
  <channel>/technician/darwin-universal/Tether_<v>_universal.dmg(.sig)          manual download
  <channel>/customer/darwin-universal/latest.json
  <channel>/customer/darwin-universal/TetherQS-<v>-universal.zip(.sig)          zipped .app
```
Each platform folder has its own `latest.json` (the technician app requests
`…/technician/{{target}}/latest.json`, `{{target}}` = `windows-x86_64` or `darwin-universal`).
A macOS manifest lists the universal build under `darwin-universal`, `darwin-aarch64` and
`darwin-x86_64`. Tether Manage reads the existing `latest.json` before writing it: platform
entries of the same version are kept, entries of another version are replaced.
Channel default `stable` (policy feature `update.channel`). `latest.json` is the Tauri updater
format plus three optional fields:
```json
{"version":"0.3.1","notes":"…","pub_date":"2026-11-04T10:00:00Z",
 "platforms":{"windows-x86_64":{"signature":"<minisign sig, as Tauri writes it>","url":"https://…/Tether_0.3.1_x64-setup.exe"}},
 "mandatory":false,"minimumVersion":"","forced":false}
```
- `mandatory`: the update must be installed before the app can be used for sessions.
- `minimumVersion`: versions below it are blocked (same effect as policy `update.minimum-version`).
- `forced`: install without asking after `update.restart-seconds`.
Clients enforce the stricter of manifest and policy. Blocking is done in the backend (session
start, accepting incoming sessions), not only in the UI.

## Custom apps (branded TetherQS downloads)

A custom app is a signed `tether_trust::custom::CustomProfile` (id, name, accent colour, welcome
text, PNG logo, a customer-profile settings `Layer`) plus a private download link. Tether Manage
signs the profile with the admin key and stores it on every relay with the same token, so the link
works on any relay. The relay never modifies the profile; TetherQS verifies the signature itself.

| Method & path | Body | Result |
| --- | --- | --- |
| `PUT /api/admin/custom/<id>` (signed) | `{"profile": <signed CustomProfile document>, "token": "<43 chars base64url>", "expires": <unix>, "channel": "stable"}` (≤ 300 KiB) | `204`. The server verifies the signature against its admin keys, runs `CustomProfile::validate`, requires `profile.id == <id>`, `custom::valid_token(token)` and `expires` in the future (≤ 366 days). Replaces an existing entry with that id (new token = old link stops working). Stored in `custom/<id>.json` (0600). |
| `GET /api/admin/custom` (signed) | – | `[{id, name, token, expires, channel, created, downloads, last_download}]` |
| `DELETE /api/admin/custom/<id>` (signed) | – | `204`; the link stops working at once. `404` if unknown. |
| `GET /q/<token>` (public) | – | The current `TetherQS-<v>.exe` of the entry's channel (from `download/<channel>/customer/windows-x86_64/latest.json`) with `custom::trailer(<signed profile>)` appended, `Content-Disposition: attachment; filename="<Name>-Support.exe"` (name reduced to `[A-Za-z0-9 _.-]`). `404` for unknown, revoked **and** expired tokens (same answer, no oracle). Rate-limited to 30 requests/min per IP. Counts downloads. |

Caddy routes `/q/*` to `tether-api`. Tokens are 256-bit random (`custom::new_token`), compared
exactly; links are not listed anywhere public. TetherQS self-updates keep the profile: after
verifying a new plain exe it re-appends its own trailer. Custom apps are Windows-only for now
(the macOS TetherQS is a `.app` bundle).

## Limits (1 GB relay VM)

`tether-api` is a single-threaded `tiny_http` service with `MemoryMax=64M`; request bodies are
streamed to disk for uploads; every JSON write is temp file + rename; no database.
